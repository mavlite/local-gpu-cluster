# Reinstall hyp02 in place, preserving VMFS

**Reinstall ESX 9.1.1 onto hyp02's boot NVMe only, in place, using the kickstart `install --disk=<boot NVMe> --preservevmfs` with `paranoid`. Then rejoin vSAN with the surviving ESA disk intact and reconcile SDDC Manager by hand.** Broadcom documents only one repair for a corrupted OSDATA volume, which is reinstalling ESXi ([KB 370038](https://knowledge.broadcom.com/external/article/370038)). The only Broadcom-documented way to rebuild a VCF-managed host is remove from cluster, decommission, reimage, commission, add back ([KB 374333](https://knowledge.broadcom.com/external/article/374333), [KB 411583](https://knowledge.broadcom.com/external/article/411583/rebuild-a-failed-esx-host-in-vcf.html)). That path would drop this 3-host cluster to 2 hosts, which cannot hold a compliant FTT=1 layout, and it triggers vSAN evacuation. The in-place route is unsupported rather than forbidden. Broadcom itself lists "rebuilt and re-added without decommission/commission" as the cause of SDDC Manager drift ([KB 314643](https://knowledge.broadcom.com/external/article/314643)), so the price is a short, known list of manual reconciliations. The lab's 9.1.1 installer source, read on 2026-10-24, makes the route safe for the three disks. The installer writes only the `--disk` target, rewrites EFI, both bootbanks and OSDATA, and re-creates the VMFS at its exact old sectors. The vSAN and tier disks are other devices and are never opened. Prevention comes down to a UPS with orderly shutdown, remote syslog and network coredump, off-host config bundles, and treating the boot NVMe as disposable.

## Why a reinstall is the only repair, and why the supported VCF route is a trap here

KB 370038 (ESXi 7.0 and 8.0) states that a corrupted OSDATA VMFS-L volume cannot be rebuilt except by reinstalling. `voma` check or dump may be used for diagnosis, but `voma` fix and advfix are unsupported on OSDATA and fail with a read-only file system error ([KB 370038](https://knowledge.broadcom.com/external/article/370038)). The SAN-datastore power-loss KB 452537 does not apply to OSDATA ([KB 452537](https://knowledge.broadcom.com/external/article/452537/vmfs-volume-severely-corrupted-following.html)). An "upgrade, preserve VMFS" run is no alternative: KB 370038 notes upgrades fail on a corrupted OSDATA, so that option would have to read the damaged volume.

For VCF, the nearest documented procedure is KB 374333 (boot media replaced on a vSAN host). In SDDC Manager you remove the host, which auto-evacuates vSAN data and removes it from the vSAN cluster. You decommission it, rebuild it with a compatible ESXi, commission it, and add it back to the original cluster. VCF then recreates the vSAN disk groups during host add ([KB 374333](https://knowledge.broadcom.com/external/article/374333)). Broadcom's design rule is four hosts for a management domain ([KB 450622](https://knowledge.broadcom.com/external/article/450622/multisite-esxi-host-requirements.html)), so this lab is already below it. Older admin guides offered "Force Remove" below the minimum and warned that too few remaining hosts can leave the vSAN datastore read-only or cause data loss ([VCF 4.5 admin guide](https://docs.vmware.com/en/VMware-Cloud-Foundation/4.5/vcf-admin/GUID-41BE1B30-8D52-43BF-8297-0059B92D723D.html)). Whether 9.x still offers Force Remove, and whether a host with an unbootable OS can be decommissioned at all, was not verified. A decommission needs a contactable host and an evacuation target, and hyp02 has neither. Deleting the host straight from vCenter is also discouraged. It leaves stale NSX host entries that blocked an NSX upgrade in VCF 9.1 ([KB 444026](https://knowledge.broadcom.com/external/article/444026/deleted-esx-host-from-vcenter-blocks-the.html)). This lab has NSX installed.

The fallback that is least bad is a temporary fourth host before any decommission, which is hardware the lab does not have. That leaves the in-place reinstall as the pragmatic route. The lab's reinstall already has an advantage the Broadcom KBs lack. KB 327032 and KB 419382 describe reinstalling "keeping the vSAN partitions intact" but warn that choosing a vSAN disk as the install target can corrupt data ([KB 327032](https://knowledge.broadcom.com/external/article/327032), [KB 419382](https://knowledge.broadcom.com/external/article/419382/esxi-host-rebooted-and-unable-to-find-t.html)). The kickstart pins the target to the Crucial CT1000P310 boot device by its `t10.` identifier. `paranoid` turns the "no VMFS found, creating a new datastore" warning into a hard stop. That warning is the one way a wrong target could silently succeed.

## What the install touches, and what has to be rebuilt by hand

**Lab-verified from the 9.1.1 build 25714478 installer source (not Broadcom documentation).** `--preservevmfs` rewrites EFI, both bootbanks and OSDATA and restores the VMFS partition at its previous start and end sectors with its old label. It errors if the VMFS starts below 4 GB. Broadcom's installer-menu KB confirms the interactive equivalent ("Install ESXi, preserve VMFS datastore") exists in 9.x, but not the kickstart flag ([KB 392956](https://knowledge.broadcom.com/external/article/392956)). Community reports say that mode keeps VMs but not host configuration ([Broadcom community](https://community.broadcom.com/vmware-cloud-foundation/discussion/lost-root-password-how-to-reset-it-how-to-preserve-existing-vms)). So the host returns with factory identity, and the lab's `%firstboot` has to re-apply SSH, NTP, MTU, the coredump file, memory tiering (`esxcli memtier enable`), the consumer-AMD workarounds, and the FQDN plus certificate regeneration. The certificate step matters. SDDC Manager stores the thumbprint from commissioning, and a changed certificate makes add-host fail with an SSLVerifyFault ([KB 432436](https://knowledge.broadcom.com/external/article/432436/add-esxi-host-to-cluster-fails-authent.html)). Commissioning also requires the certificate SAN to match the FQDN ([KB 327187](https://knowledge.broadcom.com/external/article/327187/unable-to-commission-hosts-due-to-certif.html)).

Config-restore is not a good shortcut. `restore_config` needs a bundle taken before the failure, the same build, and a matching UUID. From vSphere 7.0 U2 the force override fails on TPM-enabled hosts ([KB 313510](https://knowledge.broadcom.com/external/article/313510)). The default bundle location, `/scratch/downloads/`, lives on the lost OSDATA. Whether `state.tgz` still holds usable ESXi 9 config (ConfigStore) is unconfirmed. Copying `/bootbank/state.tgz` and `/altbootbank/state.tgz` off the host before reinstalling costs nothing, if the installer shell can reach them. Treat them as evidence, not a plan.

Several things outside the host will be stale after a same-FQDN reinstall. The `svc-vcf-<short>` account is gone, so SDDC Manager shows the host disconnected. Recreate it with `esxcli system account add` and `esxcli system permission set --role Admin` using the password from SDDC Manager's Password Manager, then remediate it there ([KB 314643](https://knowledge.broadcom.com/external/article/314643)). The root password must match SDDC Manager's record, and lockdown mode blocks validation ([KB 426417](https://knowledge.broadcom.com/external/article/426417/synchronize-domain-inventory-failed-on.html)). vCenter's stored thumbprint, NSX transport-node state, VDS membership, and vmk configuration all need checking. On vCenter 9.0, a thumbprint mismatch can crash vpxd, so inspect before bulk reconnecting hosts ([KB 405750](https://knowledge.broadcom.com/external/article/405750/error-the-sslthumbprint-and-sslcertifica.html)). The host must also match the cluster's vLCM image (build 25714478). VDS, NSX and vLCM recovery after an OSData loss has no 9.x source and is inference from general vSphere behavior.

## The vSAN ESA disk should rejoin, but nobody documents that for ESA

Broadcom's rebuild procedure is: remove the old host entry from vCenter, install the identical build without touching vSAN partitions, add the host back, configure the management and vSAN vmks and `vmkping` in both directions, then drag it into the cluster. That pushes the correct unicast agent list to all hosts. The CLI fallback uses the Sub-Cluster UUID taken from a surviving host: `esxcli vsan cluster join -x -u <SubClusterUUID>`, where `-x` is the ESA flag ([KB 327032](https://knowledge.broadcom.com/external/article/327032)). The rebuilt host gets a new Local Node UUID while the Sub-Cluster UUID stays the same ([KB 419382](https://knowledge.broadcom.com/external/article/419382/esxi-host-rebooted-and-unable-to-find-t.html)). ESA NVMe devices stay "logically claimed by a vSAN Storage Pool" and the installer does not overwrite them ([KB 399567](https://knowledge.broadcom.com/external/article/399567/unable-to-add-the-host-to-sddc-manager-f.html)). The 2014 OSA-era post says ESXi re-claims devices holding vSAN data after a reinstall ([William Lam](https://williamlam.com/2014/07/does-reinstalling-esxi-with-an-existing-vsan-datastore-wipe-your-data.html)). No source states that an ESA pool re-attaches with its data after a reinstall, so the first rejoin is an experiment with a defined exit.

The cluster's exposure is what drives the ordering. With hyp02 down, vSAN starts rebuilding absent components after 60 minutes by default. A 3-node cluster has nowhere to rebuild, so objects stay readable but non-compliant ([KB 446168](https://knowledge.broadcom.com/external/article/446168/data-resync-taking-a-longer-time-while-p.html)). Adaptive RAID-5 on up to 5 hosts is 2+1 ([community thread](https://community.broadcom.com/vmware-cloud-foundation/discussion/vsan-esa-adaptive-raid-failures-effect-on-usable-capacity)). So any failure on hyp01 or hyp03 while hyp02 is down means data loss. The survivors must not be rebooted or put in maintenance mode (inference from the policy math). If the disk re-attaches, only deltas resync. If it must be wiped, hyp02's share (about a third of used capacity for 2+1) rebuilds over the network. The wipe is `esxcli vsan storagepool remove`, `esxcli vsan cluster leave`, then `partedUtil delete`, or Erase Partitions in the client. Reclaim is by Managed Disk auto-claim or `esxcli vsan storagepool add -d` ([KB 399567](https://knowledge.broadcom.com/external/article/399567/unable-to-add-the-host-to-sddc-manager-f.html), [KB 326509](https://knowledge.broadcom.com/external/article/326509/vsan-health-service-cluster-health-vsa.html)).

## Recommended procedure

Marking: **[B]** is Broadcom-documented, **[L]** is lab-verified from installer source or lab design, **[I]** is inference.

1. **Stabilize and capture (do not touch hyp01 or hyp03 except to read).** On a survivor run `esxcli vsan debug object health summary get` and confirm nothing is inaccessible. Record `esxcli vsan cluster get` (Sub-Cluster UUID) and the storage policy in use. Back up anything critical. Do not enter maintenance mode on a survivor. Raise the object repair timer above the expected downtime ([KB 446168](https://knowledge.broadcom.com/external/article/446168/data-resync-taking-a-longer-time-while-p.html)). [B] for the checks and timer, [I] for the no-reboot rule. Because Minimal mode has vCenter and SDDC Manager off, confirm which host runs the management VMs and that they sit on hyp01 or hyp03 before hyp02 goes down further.
2. **Collect evidence from hyp02 before wiping.** If any shell works (installer shell is enough), copy `/bootbank/state.tgz`, `/altbootbank/state.tgz`, and readable `/var/log` content off to a workstation. Optionally run `voma -m vmfs -f check` read-only against the OSDATA partition. KB 370038 quotes `-m vmfs`, and the invocation is unverified ([KB 370038](https://knowledge.broadcom.com/external/article/370038)). Also record the boot device's `t10.` ID and confirm in the installer that it is not the CT4000P310 or the Samsung. [I]
3. **Disconnect hyp02 in vCenter if it is running** (disconnect, do not remove from SDDC Manager, do not decommission). Leave the NSX and SDDC Manager records as they are for now. [I], contrary to KB 374333, for the reasons above.
4. **Publish the generated kickstart and arm hyp02 only.** Check that it contains `paranoid`, the exact `--disk=` `t10.` ID of the CT1000P310, and `--preservevmfs` (and neither `--overwritevmfs` nor `--novmfsondisk`). [L] Arm the per-MAC PXE directory, power-cycle hyp02, and **disarm it as soon as it has fetched the kickstart**, or it will reinstall in a loop. [L]
5. **Expected result: install completes.** If `paranoid` aborts on "no VMFS found" or "VMFS below 4 GB", stop. That means the VMFS is already damaged or the wrong disk was targeted. Do not remove `paranoid` to make it go. Fall back to a manual install via the installer menu ("Install, preserve VMFS") after reading the partition table, and if no VMFS exists, accept that the datastore is lost. [L], with fallback inferred.
6. **%firstboot, then verify.** Confirm SSH, NTP, vSwitch0/vmk0 MTU 1500 (the management VLAN; the 9000 fabric MTU belongs to the VDS vmks), the coredump file, memtier (`esxcli memtier` status shows the Samsung tier, and the BIOS settings are unchanged), and the consumer-AMD workaround lines in `/etc/vmware/config`. If memtier enable refuses because of a leftover tier partition, use the 9.1 wipe/delete path from [Lam](https://williamlam.com/2026/08/quick-tip-the-fastest-way-to-clear-partitions-for-esx-reinstallation.html) on the tier device only. [L] for config, [I] for the tier fallback. Verify the datastore (`esxcli storage vmfs extent list`) shows the old label and the VMs on it are unchanged.
7. **Rebuild identity for the cluster.** Create the vSAN and management vmks, and `vmkping` both survivors. In vCenter, reconnect or re-add hyp02 (accept the new thumbprint). Add it to the VDS and cluster. If the drag-in does not join vSAN, run `esxcli vsan cluster join -x -u <SubClusterUUID>`. Check `Local Node Health State HEALTHY` and `vSAN ESA Enabled: true`. [B], except thumbprint acceptance, which is [I].
8. **Decision point: did the pool re-attach?** Run `esxcli vsan storagepool list`, `vdq -qH`, and the object health summary. **If the CT4000P310 shows as a member of the pool and objects resync: done, wait for resync to finish.** **If the disk is ineligible/unhealthy and the pool is not mounted, try a reboot of hyp02 only (the maintenance-mode UNKNOWN symptom has a documented fix ([KB 436164](https://knowledge.broadcom.com/external/article/436164/troubleshooting-unhealthy-disk-alerts-on.html))).** Stale-join errors: `esxcli vsan cluster leave`, then rejoin ([KB 454125](https://knowledge.broadcom.com/external/article/454125/unable-to-add-a-rebuilt-esxi-host-to-a.html)). Only if that fails, wipe and reclaim as in the section above, accepting the full network rebuild with the cluster running degraded throughout. [B] for the commands, [I] for the sequence.
9. **Reconcile VCF.** Power on SDDC Manager and run inventory sync. Recreate `svc-vcf-<short>` on hyp02, then remediate in Password Manager (and check root). Check NSX Manager for a stale or disconnected transport node and delete it if the host appears duplicated ([KB 444026](https://knowledge.broadcom.com/external/article/444026/deleted-esx-host-from-vcenter-blocks-the.html)). Confirm vLCM compliance and SSL thumbprint match in SDDC Manager. If add or validation still fails on thumbprint, DNS port 53 is a known cause ([KB 441245](https://knowledge.broadcom.com/external/article/441245/vcf-9x-host-validation-fails-with-ssl-th.html)). [B] for the individual fixes, but there is no single documented in-place procedure. If SDDC Manager will not reconcile, the remaining option is the decommission/commission cycle, ideally with a temporary fourth host.
10. **Restore Minimal mode and take a baseline.** Run `vim-cmd hostsvc/firmware/sync_config` and `backup_config`, and store the bundle off-host ([KB 313510](https://knowledge.broadcom.com/external/article/313510)).

## Preventing a repeat

The root cause is a consumer NVMe with no confirmed capacitor-based power-loss protection losing acknowledged writes. Crucial markets "power loss immunity" for the P310, which StorageReview does not define as hardware PLP ([StorageReview](https://www.storagereview.com/review/crucial-p310-ssd-review)). No source documents ESXi's flush/FUA behavior on DRAM-less NVMe. The firmware mismatch between boot (V8CR001) and vSAN (V8CR010) cannot be assessed because Crucial's changelog was not retrievable. Compare `esxcli nvme device get` with Crucial Storage Executive output and update the boot drive if a newer image exists.

The first control is a UPS with automated shutdown. NUT runs best on a machine that outlasts the hosts, with the UPS off-delay longer than the full ESXi shutdown, and VM stop order and delays set. Sources for this are older community material ([dev.to NUT guide](https://dev.to/merbayerp/safely-shutting-down-your-homelab-during-a-ups-outage-with-nut-33g3)). Second, configure remote syslog (`esxcli system syslog config set --loghost`), which would have kept the pre-failure logs ([KB 318939](https://knowledge.broadcom.com/external/article/318939/configuring-syslog-on-esxi.html)). In VCF, the "automatically configure all ESXi hosts" option can overwrite manual `logHost` values, so set it at the VCF layer too ([KB 448889](https://knowledge.broadcom.com/external/article/448889/esxi-sysloggloballoghost-settings-contin.html)). Add a network coredump collector (`esxcli system coredump network set ...`), which is unsupported on NSX N-VDS interfaces ([KB 344063](https://knowledge.broadcom.com/external/article/344063/configuring-the-network-dump-collector-s.html)). Third, keep write-heavy items off the failing volume. Persistent scratch on the local datastore is an option ([KB 317689](https://knowledge.broadcom.com/external/article/317689/)) but it shares the same NVMe. Fourth, take off-host config bundles on a schedule. Fifth, accept that the boot NVMe is disposable, keep the kickstart as the source of truth, and consider moving the boot role to a drive with documented PLP.

## Conclusion

The corrupted OSDATA turns a single-disk fault into a VCF problem because the supported recovery (decommission, commission) assumes spare hosts the lab lacks. The new `--preservevmfs` plus `paranoid` kickstart changes the risk profile. The step that most worried the research notes, whether the installer would touch the vSAN or tier disks or the local VMFS, is answered by the installer source. The open risk moves to what no source covers: ESA pool re-attachment, VDS and NSX recovery on 9.1.1, and SDDC Manager acceptance of an in-place rebuild.

The lab should treat the first rebuild as a rehearsed experiment with stated exits, record the real outcomes, and fold them into the build record. The most valuable follow-ups are cheap. Compare vSAN node UUID with `esxcli system uuid get` on hyp01 and hyp03. Check whether the management domain is native or imported. Test the kickstart on a non-critical disk. Take a config bundle from each host now.
