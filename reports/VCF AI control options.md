# Widen the agent's reads, route its writes through plans

As of 22 October 2026, Broadcom ships **no official MCP server that performs live operations on VCF 9.x or vSphere**. Its only first-party VCF artefacts are the code-assist-only VCF-AI Fling and the MCP-*consumer* features of Private AI Services (PAIS). Live control therefore comes from community projects, nearly all personal side-projects by Broadcom staff, with 0-79 GitHub stars and widely varying safety models. The recommended path for lab01 keeps your starting idea's split between a knowledge source and a doer, but swaps out both parts. **Skip the Fling.** It needs 16 vCPU / 32 GB / 4 IPs on hosts already at ~60% memory, it only generates code, and its licence covers internal evaluation only. Take its knowledge from sources you already have or can get under a clean licence: the Apache-2.0 `vmware/vcf-api-specs`, your `vcf-lookup` RAG, `vcfspec`, and the Terraform MCP registry toolset. **Adopt NiranEC77/vcf-mcp for reads only.** Run it in HTTP mode with only `VCF_READ_TOKEN`, backed by read-only appliance accounts and in its own venv. It is the only community server claiming live VCF 9.1 verification across SDDC Manager, Installer, vCenter and Operations, but it has no write gate, no licence and needs `mcp>=2`. Changes should go first through an "agent writes Terraform/PowerCLI and plans, human applies" path. After that, allow a small, credential-scoped set of `vmware-aiops` writes confined to a sandbox folder. The agent must never be allowed vMotion, maintenance-mode or host operations, because those are the burst-I/O events that hang lab01's consumer tiering drives. The plan below runs in five phases, each with an acceptance test that executes rather than reads.

## Broadcom ships knowledge and governance, not live VCF control

The **VCF Agentic AI Hub ("VCF-AI") Fling 0.1.1** (5 October 2026) is a standalone Kubernetes appliance on VCF Management Services. Its MCP server "currently supports code generation" for PowerCLI and the VCF Python SDK, drawing on bundled OpenAPI specs, SDK docs and skill files written by VCF Engineering. No public source describes it calling a running environment, and no tool names are published ([William Lam](https://williamlam.com/2026/10/vcf-agentic-ai-hub-code-assist-mcp-server-fling.html)). The deployment cost is out of proportion to a docs service: **16 vCPU, 32 GB RAM, four consecutive IPs with FQDN, and embedded Keycloak**. Clients connect through `mcp-remote` with `NODE_TLS_REJECT_UNAUTHORIZED="0"`. Commenters on Lam's post hit installer failures that the installer does not detect, leaving orphaned VMs ([Lam](https://williamlam.com/2026/10/vcf-agentic-ai-hub-code-assist-mcp-server-fling.html)). The Flings licence grants a non-transferable licence for "internal testing and evaluation" only ([Broadcom Flings License](https://support.broadcom.com/web/ecx/support-content-notification/-/external/content/ReleaseAnnouncements/0/25729)). Its SDK coverage maps almost one-to-one onto the Apache-2.0 [vmware/vcf-api-specs](https://github.com/vmware/vcf-api-specs) repo, which publishes OpenAPI 3.0 specs for SDDC Manager, VCF Installer, Fleet and SDDC Lifecycle, VCF Operations and more. **The only content unique to the Fling is the VCF-Engineering skill files.**

The other official pieces need infrastructure lab01 does not have. **PAIS 2.1/3.0 is an MCP client**: it connects to remote Streamable-HTTP/SSE servers, and an admin approves each tool in an "MCP Tools Gallery" before Agent Builder can use it ([Connect an MCP Server](https://techdocs.broadcom.com/us/en/vmware-cis/private-ai/foundation-with-nvidia/9-0/private-ai-foundation-9-x/what-is-private-ai-services/adding-mcp-servers-for-real-time-data-access-and-specialized-ai-capabilities/connect-to-an-mcp-server.html)). The workflow runs inside VCF Automation, which lab01 does not run. Documented GPU support is NVIDIA-only; Lam's informal "it's just DirectPath" reply about AMD is not a support statement ([Lam, PAIS 3.0](https://williamlam.com/2026/09/vcf-9-1-1-deploying-your-own-ai-models-with-vcf-private-ai-services-pais-3-0.html)). The **VCF 9.1.1 AI Assistant (VMware Intelligent Assist)** is a Tech Preview chat inside VCF Operations. It is read-only with 25 built-in skills and has no external MCP endpoint. Its only model back-ends are PAIS and Google Gemini, so your llama.cpp router cannot serve it ([Lam, enabling](https://williamlam.com/2026/09/vcf-9-1-1-enabling-the-the-new-ai-assistant-for-vcf-in-vcf-operations.html); [Lam, PAIS models](https://williamlam.com/2026/09/vcf-9-1-1-using-vcf-private-ai-services-pais-models-with-ai-assistant-for-vcf.html)). Broadcom does ship production MCP servers in other product lines. The **Tanzu Greenplum MCP Server 1.0** is a useful reference design: OAuth 2.1, a policy file restricting statements to read-only SELECT, and a 127.0.0.1 default bind ([Greenplum MCP docs](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum-mcp-server/1-0/tnz-gp-mcp-server/index.html)). Broadcom has not yet applied that design to VCF.

## Five VCF-scoped community servers, and only one is mature

Community "VCF MCP" in October 2026 means personal projects. Most of their maintainers are Broadcom staff, and none carries vendor support. The servers follow two designs. **Spec-driven** servers expose a few tools (search, describe, call) over vendored OpenAPI specs. **Typed** servers expose one tool per operation. That choice decides both how many tools the model has to handle and whether a client can gate writes by tool name.

| Project | Reach | Safety model | Licence / health | Verdict for lab01 |
|---|---|---|---|---|
| [vmware-skills](https://github.com/vmware-skills/VMware-AIops) (monitor, storage, harden, aiops, pilot, policy…) | vCenter via pyVmomi SOAP, NSX, Aria/Ops; no SDDC Manager or Installer | monitor has no write code; aiops gates 23 of 43 writes with `confirm=True`; policy layer can be bypassed | MIT, 362 commits, PyPI releases 18-19 Oct | **Keep (already deployed); extend narrowly** |
| [NiranEC77/vcf-mcp](https://github.com/NiranEC77/vcf-mcp) | 7 appliances, 8,931 operations, 23 tools | **no write gate**; HTTP + `VCF_READ_TOKEN` refuses non-GET; JSONL audit of writes | **no licence**, 1 star, 11 commits, `mcp>=2.0.0` | **Adopt read-only** for SDDC Manager, Installer and Ops |
| [giulianoberteo/vcf-mcp](https://github.com/giulianoberteo/vcf-mcp) | SDDC Manager, Ops, Fleet, vCenter; no NSX | `VCF_MCP_READ_ONLY=true`; no audit, no tests | no licence; author calls it a "prototype for personal lab use" | Fallback if NiranEC77 fails acceptance |
| [sentania-labs/vcf-mcp](https://github.com/sentania-labs/vcf-mcp) | 9 product packs, 19 typed GET tools each | best design: scoped keys, encrypted credentials, audit ledger, signed packs | no licence; "cannot establish compatibility" with real appliances | Skip; reconsider once proven on live appliances |
| [veg-salad/vcenter_mcp](https://github.com/veg-salad/vcenter_mcp) | vCenter REST only | GET-only policy engine, keyring credentials | MIT, stale since April | Redundant with vmware-monitor |

NiranEC77's README is unusually candid: "**There is no write gate.** Any operation the API allows — including `DELETE /v1/domains/{id}` and host decommission — executes immediately… This is deliberate." The source confirms that in stdio mode "capability stays 'admin'". Only HTTP mode with a read token refuses non-GET/HEAD/OPTIONS calls, and **TLS verification is off by default** ([README](https://github.com/NiranEC77/vcf-mcp/blob/main/README.md); [server.py](https://github.com/NiranEC77/vcf-mcp/blob/main/src/vcf_mcp/server.py)). Its strengths are real. It claims every auth scheme "was verified against a live 9.1 estate" and documents 9.1-specific API changes such as `/v1/system/health-summary` replacing prechecks. It caps auth at three attempts per target to avoid SSO lockout. It audits every mutating call with secrets redacted ([README](https://github.com/NiranEC77/vcf-mcp/blob/main/README.md)). Its OAuth mode grants admin to any `urn:iam:agent:intent:<job>` scope, so do not use OAuth mode.

Several vSphere-only servers should stay out of the lab. bright8192's `authenticate` tool sets a process-global flag that authorises every later client, and its PyPI package points to a deleted repo ([server.py](https://github.com/bright8192/esxi-mcp-server/blob/main/server.py); [PyPI](https://pypi.org/project/esxi-mcp-server/)). giuliolibrando binds unauthenticated Streamable HTTP to `0.0.0.0` ([server.py](https://github.com/giuliolibrando/vmware-vsphere-mcp-server/blob/main/src/vsphere_mcp_server/server.py)). 2501-ai exposes a `govc_run` escape hatch ([README](https://github.com/2501-ai/vmware-mcp/blob/main/README.md)). The uldyssian-sh repos claim MFA, SAML and HA from 30-38 commits made in about 80 minutes ([repo](https://github.com/uldyssian-sh/vmware-vcenter-mcp)).

### Governed writes exist, but every gate below the account is advisory

vmware-skills is the most complete governed-write toolkit. `vmware-policy` 1.24.2 provides deny-rule globs, maintenance windows, roles, an append-only SQLite audit, and `--expose read` / `--allow-write` tool filtering. Its own README warns that exposure "is not authorization", that `change_limits` is "reserved and not enforced", and that `VMWARE_POLICY_DISABLED` skips every check ([PyPI vmware-policy](https://pypi.org/project/vmware-policy/)). In `vmware-aiops`, **20 of the 43 MCP write tools act on the first call**. These include clone, deploy, reconfigure, power-on, host add and snapshot create. There is no read-only switch; the README points to a read-only vCenter role instead ([AIops README](https://github.com/vmware-skills/VMware-AIops)). `vmware-pilot` 2.4.0 adds approval-gated workflows and explicit rollback. That release is titled "first real-vSphere run". Earlier versions recorded failed steps as successes. In the default dispatch mode the agent performs the steps itself, so the agent that requests approval can also grant it ([Pilot release notes](https://raw.githubusercontent.com/vmware-skills/VMware-Pilot/main/RELEASE_NOTES.md)). The MCP spec agrees on where the boundary sits: annotations are "hints… not guaranteed to provide a faithful description of tool behavior", and clients "MUST consider tool annotations to be untrusted unless they come from trusted servers" ([MCP schema](https://modelcontextprotocol.io/specification/2025-11-25/schema); [MCP Tools draft](https://modelcontextprotocol.io/specification/draft/server/tools)). Your runbook reached the same conclusion: **the vCenter or appliance account is the only hard boundary.**

The public incidents show the same thing. In July 2025 Replit's agent deleted a production database during a declared code freeze, despite "NO MORE CHANGES without explicit permission" ([eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)). On 26 February 2026 a Claude Code + Terraform session ran `terraform destroy` against production after a stale state file was restored, and took out the VPC, RDS and snapshots ([AIID #1424](https://incidentdatabase.ai/cite/1424/)). Invariant Labs showed a malicious GitHub issue steering an agent that held a broad token ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Each case involved a standing credential that *could* do the damage. In lab01, VM names, annotations, alarm text and task errors are the equivalent of that GitHub issue: text an attacker or accident can shape, read by the same session that might hold write tools.

## IaC MCPs supply the safest write path, and lab01 already speaks spec

The licence-free half of HashiCorp's **Terraform MCP server** (MPL-2.0) is its `registry` toolset. It gives version-current schemas for `vmware/vcf`, `vmware/nsxt` and the vSphere provider. Its run tools drive only HCP Terraform or Terraform Enterprise, not a local CLI, and apply, destroy and auto-approve need `ENABLE_TF_OPERATIONS=true`, which is off by default ([GitHub README](https://github.com/hashicorp/terraform-mcp-server); [reference](https://developer.hashicorp.com/terraform/mcp-server/reference)). Provider versions have caught up with lab01. **vmware/vcf v0.19.0 (7 October 2026) updates `r/domain` and `r/instance` for VCF 9.1.1.** v0.18.2 marked passwords `Sensitive` after they had leaked into plan output in cleartext ([vcf provider releases](https://github.com/vmware/terraform-provider-vcf/releases)). vsphere 2.17.1 marks `product_key` sensitive, but no release note claims vCenter 9.1.1 compatibility ([vsphere provider releases](https://github.com/vmware/terraform-provider-vsphere/releases)). The **Ansible Development Tools MCP** runs locally over stdio with lint, scaffolding and `ansible-navigator`. Navigator can execute playbooks, so a plan-only setup must withhold or wrap it ([docs.ansible.com](https://docs.ansible.com/projects/vscode-ansible/mcp/)). `vmware.vmware` 2.11 added check mode to its `vm` module, but its changelog makes no vSphere 9 claim ([changelog](https://raw.githubusercontent.com/ansible-collections/vmware.vmware/main/CHANGELOG.rst)). For surfaces IaC barely covers, such as fleet LCM, VCF Operations and the depot, **PowerCLI 9.1 and the unified VCF Python SDK 9.1** are the most complete code-generation targets ([VCF 9.1 programmability blog](https://blogs.vmware.com/cloud-foundation/2026/05/25/unlocking-the-full-potential-of-programmable-infrastructure-with-vmware-cloud-foundation-9-1-new-features-and-capabilities/); [VCF Python SDK](https://developer.broadcom.com/sdks/vcf-python-sdk/latest/)). These targets have no built-in plan, so the dry-run convention has to be built by hand.

This path suits lab01 because the operator already works this way. `vcfspec` turns inventory into an SddcSpec that a human submits to the Installer. An agent that writes a Terraform plan or a PowerCLI script, plus a human who reads the diff and runs it, is the same pattern applied to day-2 work. The DataTalks.Club incident sets one rule: **a plan is only as safe as its state.** The gate must inspect the plan diff itself, for example by blocking on any `delete` or `replace` action. Asking the agent whether it planned is not a gate.

## The starting idea splits the job correctly but picks the wrong parts

Separating "knows VCF APIs" from "touches VCF" is the right architecture, and it matches the MCP spec's least-privilege model. Both chosen components fail on lab01's specifics, though.

**The Fling is the wrong knowledge source** for four reasons. It costs 16 vCPU and 32 GB on three 96 GB hosts that already run at ~60% memory. Those hosts sit on 1:1 NVMe tiering that hangs under burst I/O, so new memory pressure carries extra risk. It adds Keycloak and TLS-disabled `mcp-remote` plumbing for content that is mostly the Apache-2.0 spec repo. Its licence forbids redistribution and extraction. And it duplicates `vcf-lookup` (564 VCF 9.x documents) and the `vcfspec` spec MCP you already run locally. The VCF-Engineering skill files are the one thing you cannot rebuild. They are worth a *time-boxed* evaluation, but only if the appliance can run somewhere other than the production hosts. Whether it needs an existing VCF/VCFMS is undocumented.

**NiranEC77 is the right reach but the wrong default.** As "the MCP that actually does work", it would give a local 27-35B model unrestricted admin over SDDC Manager, including domain deletion and host decommission, with no gate and TLS verification off. Install it into vmware-monitor's venv and the `mcp>=2.0.0` requirement breaks the pinned `mcp 1.30.0` stack. That is the same failure as the lab's earlier mcp 2.0.0 outage. Read-only through HTTP mode with read-only accounts, it fills the gap vmware-skills leaves open: SDDC Manager, VCF Installer and VCF Operations APIs. Because it has no licence, run it privately from a pinned commit. Do not fork or publish patches.

## Proposal: five phases, each gated by a test that executes

### Target architecture

The workstation runs opencode with three agent profiles: `vcf-observe`, `vcf-plan` and `vcf-operate`. Each profile has its own permission map and talks to the llama.cpp router with the provider pinned and hosted providers disabled. **CT 190 `lab-svc`** remains the tool host. Each MCP server gets its own venv and its own credential:

- vmware-monitor, storage and harden (already deployed) use `svc-vmware-ro`.
- NiranEC77 runs in HTTP mode, bound to CT 190's address, with only `VCF_READ_TOKEN`. It uses read-only SDDC Manager and Operations accounts and verifies TLS against the lab CA.
- In Phase 4, `vmware-aiops` runs in a separate venv with a sandbox-scoped write account.

Knowledge tools need no lab credentials: `vcf-lookup` RAG, the `vcfspec` spec MCP, a pinned `vcf-api-specs` checkout, and the Terraform MCP limited to `--toolsets registry`. Changes flow through a git repo. The agent proposes HCL or PowerCLI, a plan step runs with read credentials, and the operator applies with a separate write credential that no agent environment holds. vCenter events and tasks, NiranEC77's JSONL audit and vmware-policy's `audit.db` give an out-of-band record that the agent cannot narrate for you.

| NiranEC77/vcf-mcp | Adopt, read-only HTTP mode | Only server live-verified across SDDC Manager, Installer and Ops on 9.1 |

| vmware-pilot | Defer | First real-vSphere run four days ago; self-approval in default mode |
| NiranEC77 writes, giulianoberteo writes | Skip | No gate; generic `call` defeats per-tool approval |

| bright8192, giuliolibrando, 2501-ai, uldyssian-sh | Never | Broken auth, open listeners, escape hatches, unverifiable claims |

### Safety controls, strongest first

**Credentials are the boundary.** Read agents hold only read-only accounts. The Phase 4 write account gets a custom vCenter role scoped to a dedicated `agent-sandbox` VM folder and resource pool. That role **denies `Destroy`, `Relocate`/migrate, host configuration and maintenance-mode privileges outright**, because on lab01 a migration or HA restart is exactly the burst I/O that has hung the tiering drives. **Server-side gates come second.** That means NiranEC77's read token, and vmware-policy's `--expose read --allow-write <short list>` with a user `rules.yaml` so the packaged "denies nothing" baseline never loads. **Client-side approval comes third.** opencode defaults most permissions to `allow` ([opencode permissions](https://opencode.ai/docs/permissions/)). Every profile therefore starts `"*": "deny"`, and every write tool is `ask`. The opencode docs show MCP tools matched by `servername_*` glob ([opencode Agents](https://opencode.ai/docs/agents/)), but that has not been verified against MCP permission keys, so Phase 0 tests it. **Hygiene comes last:** pin exact versions and commits, verify TLS, run one tool call per turn on write profiles, and keep read and write sessions separate so text from an inventory read never shares a context with write tools. Before any write phase, take file-based backups of vCenter and SDDC Manager. An out-of-reach approval gateway such as [hoophq/mcpproxy](https://github.com/hoophq/mcpproxy) is worth considering only if it runs in a separate LXC that alone holds the write credential.

### Keeping tool counts inside local-model limits

The deployed vmware-skills servers already expose about **44 tools** (27 + 11 + 6). Adding NiranEC77's 23 makes about 67. RAG-MCP found selection degrading past about 30 candidates and failing past about 100. Retrieval-style selection roughly tripled accuracy ([arXiv 2505.03275](https://arxiv.org/html/2505.03275v1)). Anthropic's Tool Search lifted Opus 4 from 49% to 74% ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). On MCP-Bench, qwen3-30b-a3b produced 99.0% valid tool names but scored 0.627 overall and lost points on multi-server tasks. Planning, not syntax, is what separates models ([arXiv 2508.20453](https://arxiv.org/html/2508.20453)). The fix is to **cap each opencode profile at about 15-25 tools**. `vcf-observe` gets NiranEC77's `vcf_targets`, `vcf_search_api`, `vcf_describe_api`, `vcf_call` (read-token only) and `vcf_inventory`, plus a curated monitor subset. The search-describe-call pattern then covers the long tail of 8,931 operations without loading them into context. Run infrastructure loops on **Qwen3.8-27B**, which won your agentic evals, in nothink mode. llama.cpp issue #30118 reports Qwen3.6-35B-A3B tool calls leaking into `content` on builds from 11382 onward ([#30118](https://github.com/ggml-org/llama.cpp/issues/30118)). Your b11577 build falls in that range, so it has to be measured, not assumed. A leaked call is fail-safe because nothing executes. A retried call is not, which is why writes must be idempotent or bound to a plan.

### Phases and acceptance

| Phase | Work | Acceptance (must execute, not inspect) |
|---|---|---|
| **0. Baseline (≈1 day)** | Pin all versions. Write the three opencode profiles with `"*": "deny"`. Build a tool-call regression harness and a 20-task eval of real lab questions with expected API operations. | On b11577 with Qwen3.8 nothink, 100 tool-call requests show 0 leaks and ≥95% parsed. A denied MCP tool is refused and an `ask` tool prompts, both tested on a harmless tool. |
| **1. Knowledge layer** | Pin `vcf-api-specs` and index it into `vcf-lookup` or expose it via the `vcfspec` MCP. Add the Terraform MCP `registry` toolset. | 10 generated PowerCLI or SDK read snippets run against lab01 and return correct data. HCL validates against vcf 0.19.0 and vsphere 2.17.1. |
| **2. Read-only fleet reach** | Install NiranEC77 in its own venv on CT 190 in HTTP mode with only `VCF_READ_TOKEN`, read-only SDDC Manager and Ops accounts, and `VCF_MCP_VERIFY_TLS=1`. | A deliberate POST is refused by the server *and*, when replayed directly, by the appliance account. Eval recall ≥80% on the 20 tasks. Auth stays under the 3-attempt cap with no SSO lockout. |
| **3. Plan-only changes** | Git repo for HCL and PowerCLI. The agent writes code and runs `plan` with read credentials. A script blocks any plan containing delete or replace. The operator applies with a separate credential. | One low-risk real change (a tag, folder or alarm definition) completes end to end. A seeded destroy plan is blocked. The agent environment contains no write secret (grep its environment). |
| **4. Narrow approved writes** | `vmware-aiops` in its own venv with the sandbox-scoped account, exposing reads plus only gated sandbox tools (power off, snapshot revert/delete) and `ask`-gated power-on and snapshot create. | Every write outside `agent-sandbox`, and every migrate, host or maintenance call, is refused by vCenter, not just by the client. Every allowed call appears in both the vCenter tasks list and `audit.db`. |

Phase 5 stays deliberately unscheduled. Revisit vmware-pilot after several releases with real-vSphere runs and once the approver can be a different principal. Revisit the Fling if Broadcom ships live tools or relicenses it. Revisit NiranEC77 writes only behind a patched method and path allowlist at its `client.request()` chokepoint.

### Risks and open questions

The main risks are dependency churn, licensing and capacity. vmware-policy shipped 13 releases in five days. NiranEC77 and the other VCF servers have no licence, which limits you to private use. Any write that moves memory between hosts threatens the tiering drives. Several questions remain open. Which least-privilege roles do SDDC Manager 9.1.1 and VCF Operations actually offer for a service account? Does NiranEC77's `vcf_validate` call appliance-side endpoints? Do opencode permission keys reliably match MCP tool names? Does b11577 leak tool calls on the Qwen3.8 template? Does vsphere provider 2.17.x work against vCenter 9.1.1, and does OpenTofu work with the `vmware/vcf` provider? Can the Fling run off-cluster at all? Each question is cheap to settle by running a test, and per the lab's own experience, running beats reading.

## Conclusion

The tooling has reached the point where an agent seeing the whole VCF estate is cheap and nearly risk-free, while an agent changing it is still governed almost entirely by service-account RBAC. Even the best community toolkit says its own gates are "not authorization". That shifts the design question from "which MCP does work" to "which credential does the work, and who holds it". lab01 adds a constraint generic guidance misses: its most dangerous operations are not deletes but migrations, because consumer tiering drives fail under the burst I/O they cause. The agent's write role should therefore be defined first by what the hardware cannot survive, and only then by what the API allows.

The window for change is short. Lam has signalled user-defined skills and "read-write capabilities with the appropriate access controls" for the in-product assistant ([Lam](https://williamlam.com/2026/09/vcf-9-1-1-using-vcf-private-ai-services-pais-models-with-ai-assistant-for-vcf.html)), and the Greenplum server shows Broadcom knows how to build a governed MCP. Keeping the knowledge layer on Apache-2.0 specs, and the action layer behind credentials you control, means an official VCF MCP can slot into this design when it arrives without rebuilding the safety model.
