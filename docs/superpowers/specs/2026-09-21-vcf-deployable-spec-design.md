# RETRACTED — "Rendering a deployable VCF 9.1.1 spec"

**Date:** 2026-09-21
**Status:** **RETRACTED.** Its central premise was false. Kept as a record of
what was wrong, what the investigation did produce, and how it was settled.

## What this document claimed

That the renderer produced an `SddcSpec` VCF would **reject**, because
`vcfOperationsSpec`, `licenseServerSpec` and `vidbSpec` were mandatory for
`workflowType: VCF`. It proposed modelling those components, adopting a
known-good 9.1.0 sample as a structural template, and making
"structurally equivalent to the reference" the acceptance test.

## Why it was wrong

The claim came from Broadcom's
[JSON specification page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/use-a-json-specification-to-deploy-vmware-cloud-foundation-or-vmware-vsphere-foundation.html).
That page's table is **`useExistingDeployment` guidance**, not a
mandatory-section list — its own preamble says it "provides guidance on certain
properties that you specify". Its `true`/`false` cells were read as
present/absent. `VidbSpec` does not even have a `useExistingDeployment`
property, which should have been the tell.

## How it was settled

The rendered spec was submitted to a real VCF 9.1.1 Installer's
`POST /v1/sddcs/validations` on 2026-09-21. The omitted sections produced **no
errors** — only informational notices that the Installer supplies them itself:

```
AUTOGENERATED_CLUSTER_SPEC.info      AUTOGENERATED_VDS_SPEC.info
AUTOGENERATED_DATACENTER_NAME.info   AUTOGENERATED_PASSWORDS.info
DEFAULT_VSP_CLUSTER_SIZE.info -> small_ha
```

## What the investigation did produce, and which stands

1. **A real defect, now fixed.** vMotion and vSAN require
   `includeIpAddressRanges` — one address per host, with addresses ending in
   `.0` and `.255` ignored by the Installer's count. The renderer already
   emitted the field when a network declared a `pool`; the example declared
   none and **no rule required one**. Now `VCF-NET-IP-POOL-MISSING` and
   `VCF-NET-IP-POOL-TOO-SMALL`, confirmed cleared by re-validation.
2. **Short hostnames are correct.** `hostSpecs[].hostname: "esx01"` and the
   full FQDN produce identical validation results; the schema says short, and
   the Installer composes the rest from `dnsSpec`. The known-good 9.1.0
   sample's use of FQDNs is not a requirement.
3. **`vlanId` remains untested.** Our schema says integer, the 9.1.0 sample
   uses a string, and the harness ran untagged so the field was never
   exercised. Still open.
4. **The acceptance test it proposed was unsatisfiable anyway.** The 9.1.0
   reference fails our vendored 9.1.1 schema in eight places (string `vlanId`s,
   `null` arrays) and carries three fields 9.1.1 does not declare, so "every
   field present" and "types match 9.1.1" could never both hold.

## The lesson worth keeping

Three separate conclusions in this project were reached by reading vendor
documentation and each was overturned by running the software: this one, the
`--overwritevsan` flag, and the per-MAC boot path. Documentation describes
intent; the installer decides. Where a question can be settled by submitting a
payload, submit the payload.
