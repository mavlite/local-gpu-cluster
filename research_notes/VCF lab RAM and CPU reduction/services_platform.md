# VCF Services Platform (VSP / VCF Management Services / VCF Services Runtime / VMSP) — reducing RAM and CPU in a homelab

Naming note: Broadcom and the community use several names for the same Kubernetes cluster. "VCF Management Services (VCFMS)" is the service layer. "VCF Services Runtime" is the node cluster as VCF Operations shows it (Build > Lifecycle > VCF Management > Components > VCF Services Runtime). "VMSP" and `vmsp-platform` are the in-cluster names. "vsp" is the installer prefix (`vspClusterSpec`, `vsp.bootstrap.*`). VCF Automation runs on a *separate* "consumption" VMSP cluster, so it is not one of the 6 VMs in question.

**Key observation about this lab:** the lab totals of 42 vCPU / 78 GB (3 × 4 vCPU/10 GB control plane + 3 × 10 vCPU/16 GB workers) exactly match the wizard's quote for the **9.1.1 "Small (High Availability)"** profile: "42 vCPU, 78 GB, 12 IP addresses" ([virtualbytes.io](https://virtualbytes.io/vcf-9-1-1-scaling-vcf-management-services-from-ha-back-to-simple/)). 10 vCPU / 16 GB is the 9.1.1 `management.small` worker machine type ([virtualbytes.io](https://virtualbytes.io/vcf-9-1-1-worker-rightsizing-poddisruptionbudgets-and-why-it-does-not-stick/)). So the lab is already on the smallest *HA* profile with right-sized workers. The remaining levers are (a) HA → Simple, which drops 2 control plane VMs, and (b) fewer workers (minReplicas 3 → 2).

## 1. Deployment sizes / profiles (9.0 vs 9.1 vs 9.1.1) and per-node vCPU/RAM

### Takeaway
In 9.1.0 the profiles were Simple-Small (1 CP + 3 × 12/24 workers), HA-Medium and HA-Large. 9.1.1 added `small_ha` and right-sized Day-0 workers to `management.small` (10 vCPU/16 GB). It also cut one worker from Simple. Worker count is not fixed: the platform computes it from installed components and autoscales it.

### Cited Findings
- 9.1 sizing table (Lam): Simple/Small = 1 × CP 4 vCPU/10 GB + 3 × workers 12 vCPU/24 GB; HA/Medium = 3 × CP 4/10 + 3 × workers 24/48; HA/Large = 3 × CP 8/12 + 4 × workers 24/48. "VCFMS determines its availability model based on the selected deployment size". In 9.1.0 the only UI path to HA was scaling to Medium or Large — [William Lam, Enabling HA for Small VCFMS](https://williamlam.com/2026/06/vcf-9-1-enabling-high-availability-for-a-small-vcf-management-services-vcfms-deployment.html)
- Small (no HA) initial total is about 40 vCPU / 82 GB RAM. Each node VM has a 100 GB base disk, and storage is about 3 TB for a small deployment. The node IP pool is 12–30 addresses (/28–/27) — [why-did-it.fail](https://www.why-did-it.fail/blog/2026-05-lets-talk-about-vcf-mgmt-svc/)
- Worker sizes from Broadcom's Log Management design: 12 vCPU/24 GB for the small Log Mgmt profile, 24/48 for medium, and 2 workers per replica for large — [Broadcom TechDocs, Log Management Detailed Design (9.1)](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/vcf-operations-design/vcf-operations-for-logs-deployment-models.html) (from the search snippet; page not fetched in full)
- 9.1.1: "VCFMS sizing optimized for Day-0". A Simple (non-HA) deployment "will now have one less VCFMS Worker Node (12 vCPU / 24GB memory)" — [William Lam, 9.1.1 reduced footprint](https://williamlam.com/2026/09/vcf-9-1-1-adopting-the-reduced-vcf-management-services-vcfms-footprint-after-an-upgrade.html)
- 9.1.1 adds the Small HA option. In the VCF Installer JSON API the size value is `"small_ha"` in `"vspClusterSpec"`. Small → Small HA is a Day-N UI action (VCF Services Runtime > Action > Scale) — [William Lam, 10 enhancements in 9.1.1](https://williamlam.com/2026/09/10-exciting-enhancements-in-vmware-cloud-foundation-9-1-1.html)
- VMware's blog cites roughly a 40% footprint reduction per deployment type compared with 9.1 — [VMware VCF blog, 2026-10-13](https://blogs.vmware.com/cloud-foundation/2026/10/13/customer-favorite-capabilities-accelerating-your-path-to-vcf-9-1-1/) (from the search snippet; not fetched). In 9.1.1 the installer defaults to Small rather than Medium — [Justin Raley](https://justinraley.com/whats-new-in-vmware-cloud-foundation-9-1-1/) (from the search snippet)
- Machine types seen live: `management.small` = 10 vCPU/16 GB (allocatable 9905m CPU / ~14.1 GiB); `management.large` worker = 16 vCPU/32 GB; CP = 4 vCPU/10 GB. The Small HA + fleet mapping is `management.small`, minReplicas 3 — [virtualbytes.io, worker rightsizing](https://virtualbytes.io/vcf-9-1-1-worker-rightsizing-poddisruptionbudgets-and-why-it-does-not-stick/)
- The 9.1.0 Small worker size presets are Small 12/24 and Medium 24/48. At about 7 workers the autoscaler replaces them with the next size up. The global config exposes `cluster.worker.size` (enum "", small, medium, large, xlarge), `cluster.worker.machineType`, `cluster.worker.minReplicas` (default "3") and `cluster.ha` — [Leaha's Blog](https://blog.leaha.co.uk/2026/07/21/vcf-9-management-services-lab-downsize/)
- "The actual number and size of worker nodes is determined by all the components that are deployed and their sizing and availability settings." Adding Real-time Metrics (16 vCPU/20 GB) triggers an extra worker — [why-did-it.fail](https://www.why-did-it.fail/blog/2026-05-lets-talk-about-vcf-mgmt-svc/)
- VVF deploys "1 x CP + 2 x WK" for VCFMS, which expands to 3 workers if Log Management is enabled. Node sizes are the same as VCF — [Lam comment reply, 9.1 lab workarounds](https://williamlam.com/2026/05/vcf-9-1-comprehensive-vcf-installer-sddc-manager-configuration-workarounds-for-lab-deployments.html)
- One 2-host lab: the wizard "Small" deployed 1 CP + 1 worker. "Small (High Availability)" deployed 3 CP + 1 worker and failed placement on 2 hosts, because HA requires a separate host per CP — [lab2prod.com.au](https://www.lab2prod.com.au/2026/10/how-i-fixed-a-failed-vcf-managed-services-platform-deployment.html) (the 1-worker count conflicts with other sources and may reflect a pre-scale-out snapshot)

### Inferences
- A 9.1.1 greenfield Simple deployment is most likely 1 CP (4/10) + 2 × `management.small` (10/16) ≈ 24 vCPU / 42 GB. This is derived from "3 workers minus one" plus the KB note that fleet deployments need more worker headroom. It is not confirmed in a sizing table.
- 9.0: I found no source describing a fleet-services VSP in 9.0. In 9.0, fleet management was a separate VM appliance. 9.1 "migrated" the fleet management VM and the new log management into the platform ([why-did-it.fail](https://www.why-did-it.fail/blog/2026-05-lets-talk-about-vcf-mgmt-svc/)). VMSP clusters in 9.0 existed for VCF Automation, and probably for the vIDB appliance mode (KB 440721 references vIDB node VMs in 9.0.x).

### Gaps
- No official Broadcom 9.1.1 sizing table was retrieved for Simple vs Small HA (CP and worker counts) or for the fleet vs instance minReplicas values. The KB script has these values in a case statement but the KB doesn't print them.

## 2. Can the lab run 1 control plane and 1–2 workers? How, and with which properties?

### Takeaway
Yes, but only unsupported. For an existing Small HA deployment, `vmsp pkg configure vmsp-platform -n vmsp-platform --set cluster.ha=false` has been proven in a 9.1.1 lab to shrink 3 CP → 1 (saving 8 vCPU / 20 GB). The steps are messy (Postgres SyncFailed nudges, a stale UI that needs a Fleet LCM restart). Workers can go to 2 via `cluster.worker.minReplicas`, provided no Day-N components are installed. For a greenfield deployment, the supported route is the Simple/"small" size in `vspClusterSpec`.

### Cited Findings
- **Proven in a lab (9.1.1, HA → Simple):** run `vmsp pkg configure vmsp-platform -n vmsp-platform --set cluster.ha=false` on a CP node as `vmware-system-user` → `sudo -i`, with `KUBECONFIG=/etc/kubernetes/admin.conf`. CAPI/KCP then removes etcd members one by one, replaces the last CP with a new VM, and moves the VIP. Total time was about 20 min — [virtualbytes.io, HA back to Simple](https://virtualbytes.io/vcf-9-1-1-scaling-vcf-management-services-from-ha-back-to-simple/)
  - The fleet-LCM and SDDC-LCM Postgres replicas dropped 3 → 2 and stuck in SyncFailed. The fix was `kubectl annotate postgresql -n vcf-fleet-lcm vcf-fleet-lcm-db sync-nudge="$(date +%s)" --overwrite` (same for `vcf-sddc-lcm/vcf-sddc-lcm-db` and `salt-raas/pgdatabase`). During the handover the Kyverno fail-policy webhook was unreachable. After the change, run `kubectl rollout restart deploy -n vcf-fleet-lcm` so VCF Operations stops showing the stale HA topology. The vIDB Postgres stayed at 3 replicas and orphaned `pgdata-*-db-2` PVCs were left behind. The author calls it unsupported, says VM snapshots are not a valid rollback (all CP VMs are rebuilt), and says to take a VCFMS backup first. The supported path is a redeploy — same source
- Conflicting statements from Lam on HA → non-HA for 9.1.0: his article says the same API method "could" scale back down, but a later comment says that once HA is enabled you cannot scale back down — [William Lam](https://williamlam.com/2026/06/vcf-9-1-enabling-high-availability-for-a-small-vcf-management-services-vcfms-deployment.html). His method is a PowerShell script `configure_small_high_availability_for_vcf_management_services.ps1` that calls a backend VCFMS API, which Broadcom does not support — same source
- Lam reports that Product Management plans HA support for the Simple model in a future 9.1.x — [William Lam](https://williamlam.com/2026/06/vcf-9-1-enabling-high-availability-for-a-small-vcf-management-services-vcfms-deployment.html)
- **Proven in a lab (9.1.0, fewer and smaller workers):** Leaha ran 1 CP plus 2 × 8 vCPU/16 GB workers without IDB/Log Mgmt, 2 × 8/16 with IDB (advanced tweaks), 3 × 8/16 with IDB + Log Mgmt, and 3 × 6/16 with advanced tweaks. Real-time Metrics needs a 4th worker. This was achieved by cutting pod CPU/memory *requests*: patches on `salt-raas` (raas, redis, `postgresinstance pgdatabase`), `salt` (salt-master, salt-minion), the `vmsp-global-config-<ver>` ReleaseTemplate `profileSmall` values (Zot, logging-operator, Antrea, node-problem-detector, Kyverno replicas 3 → 2, helm-controller, support-bundle, cert-manager cainjector), and the argo-workflows and strimzi-kafka-operator ReleaseTemplates. The author says "NOT even remotely supported" and it was untested across upgrades — [Leaha's Blog](https://blog.leaha.co.uk/2026/07/21/vcf-9-management-services-lab-downsize/)
- Worker sizing keys on PackageDeployment `vmsp-platform`: `vmsp pkg configure vmsp-platform -n vmsp-platform --set cluster.worker.size=small --set cluster.worker.machineType=management.small --set cluster.worker.minReplicas=3`. "minReplicas is a floor, not a fixed count" — the cluster autoscaler (max 20) scaled 3 → 4 → 3 during a rollout — [virtualbytes.io, worker rightsizing](https://virtualbytes.io/vcf-9-1-1-worker-rightsizing-poddisruptionbudgets-and-why-it-does-not-stick/)
- Lam (9.1 lab workarounds) gives no node-count or size override for VCFMS. The only lab properties are the bootstrap timeouts `vsp.bootstrap.task.timeout.minutes = 240` and `vsp.bootstrap.command.timeout.minutes=200` in `/etc/vmware/vcf/domainmanager/application.properties`, followed by `systemctl restart domainmanager` — [William Lam, 9.1 lab workarounds](https://williamlam.com/2026/05/vcf-9-1-comprehensive-vcf-installer-sddc-manager-configuration-workarounds-for-lab-deployments.html)
- A reader shrank a 12-vCPU worker to 8 vCPU on 8-core NUCs (3 × 64 GB), and pods then stalled on Telemetry — same Lam post, comments

### Inferences
- For this lab: HA → Simple frees 2 × (4 vCPU/10 GB) = 8 vCPU / 20 GB configured. Setting `cluster.worker.minReplicas=2` (if no Log Mgmt or Real-time Metrics is installed) would free another 10 vCPU / 16 GB. That would bring the cluster to about 24 vCPU / 42 GB, the presumed 9.1.1 Simple footprint. The KB says fleet deployments need extra worker headroom and the script picks a higher minimum replica count for them, so the scheduler may need Leaha-style request trimming before 2 workers fit. The autoscaler may also add a third worker back if pods go Pending. This is speculative and not tested by any source at 9.1.1 with minReplicas=2.
- A smaller custom machine type below `management.small` (e.g. 8/16) is shown only for 9.1.0 (Leaha), and the post does not show the machineType edit itself. Values set by hand are overwritten whenever the platform recomputes the worker profile (component install/removal, likely patching).

### Gaps
- No source shows a 9.1.1 lab running Simple + 2 workers *after* converting from Small HA.
- No source documents a feature flag in the VCF Installer that forces 1 CP / 1 worker beyond choosing the Simple size.
- The exact installer JSON key holding `"small_ha"` inside `vspClusterSpec` (likely a size/deploymentSize field) was not shown verbatim.

## 3. Resizing node VMs after deployment — supported paths, and what happens with a direct vSphere edit

### Takeaway
The only supported footprint reductions are the KB 455842 right-sizing script (upgraded deployments with Day-0 components only) and choosing the size at deploy time. Nodes are Cluster API Machines, and machine type is immutable: a size change rolls brand-new VMs. A direct vSphere edit fights the reconciler, which matches the observed ~6 s auto-restart.

### Cited Findings
- **Supported (Broadcom KB 455842):** this applies to brownfield 9.1 → 9.1.1+ deployments with Day-0 components only. Run `rightsize-day0-workers.sh` on a CP node (`vmware-system-user` → root). It aborts if Log Management or Real-time Metrics is installed, or if `cluster.type` is `consumption`. It auto-detects profile/HA/fleet from the `vmsp-platform` PackageDeployment and sets the worker size, machine type and minimum replica count. Check progress with `kubectl get pd vmsp-platform -n vmsp-platform` until it shows `Successful`. Workers are replaced one at a time, so do it in a maintenance window. It does not apply to VVF — [Broadcom KB 455842](https://knowledge.broadcom.com/external/article/455842)
- The VCF Inspector Fling also wraps the post-upgrade script workflow — [William Lam](https://williamlam.com/2026/09/vcf-9-1-1-adopting-the-reduced-vcf-management-services-vcfms-footprint-after-an-upgrade.html)
- Mechanics: "Machine type is immutable in CAPI". Changing worker size creates a new VSphereMachineTemplate and MachineSet, then rolls all workers. The MachineDeployment has nodeDrainTimeout, nodeVolumeDetachTimeout and nodeDeletionTimeout of 1800 s each. Zalando Postgres PDBs (`minAvailable: 1`, single replica, one DB per worker through anti-affinity) block every drain. After 30 min CAPI force-deletes the VM and the DBs recover via WAL replay (affected: SDDC LCM, Identity Broker). The workaround is to delete the blocking pod directly (`kubectl delete pod -n vcf-sddc-lcm vcf-sddc-lcm-db-0`), because direct deletes bypass the PDB. PDBs are operator-managed and get reconciled back if patched — [virtualbytes.io](https://virtualbytes.io/vcf-9-1-1-worker-rightsizing-poddisruptionbudgets-and-why-it-does-not-stick/)
- Re-installing Log Management recomputed the worker profile and rolled the workers to `management.large` (16/32). When forced onto small workers, Log Mgmt's requests (log-processor 3 CPU/6Gi, log-store 5 CPU/10Gi, and others: 8600m / 16.6Gi total) did not fit ~9905m / 14.1 GiB allocatable, so `log-store-0` stayed Pending. The lesson: decide Day-N components before rightsizing — same source
- Broadcom on VCF Automation (separate cluster): "Scaling down a VCF Automation deployment is strictly not supported … Administrators must not manually reduce virtual machine configurations or remove nodes from the cluster" — [Broadcom KB 434650](https://knowledge.broadcom.com/external/article/434650/scaling-down-your-vcf-9-environment.html). The KB covers VCFA only, not the management services runtime
- Related Broadcom KBs found but not read: safe shutdown of all VCF Services Runtime nodes ([KB 440874](https://knowledge.broadcom.com/external/article/440874/)); VMSP node provisioning failures during scaling/lifecycle ([KB 434922](https://knowledge.broadcom.com/external/article/434922/unable-to-provision-new-nodes-for-vmsp-c.html))

### Inferences
- A direct vSphere edit of a node VM (vCPU/RAM) is very likely reverted or fought. CAPI holds the VSphereMachineTemplate as the desired spec, and the restart-after-shutdown behaviour shows an active reconciler. Shrinking a node below its pods' requests would also leave pods Pending and trigger the autoscaler to add a node. No source tested a direct VM edit on 9.1.x, so this is inferred, not proven. Use the safe-shutdown KB 440874 rather than guest shutdowns.
- Reservation/shares-style tuning in vSphere (e.g. memory shares Low) leaves the CAPI spec unchanged, so it probably survives better than a size change. It frees no configured RAM, only priority. This is not tested by any source.

### Gaps
- No source tested whether vCenter-side settings (shares, limits, memory reservation removal) persist across CAPI rollouts.

## 4. Which VSP-hosted services are optional, and how to undeploy them

### Takeaway
The Day-0 set is mandatory: fleet LCM, SDDC LCM, Salt master and Salt RaaS, telemetry, identity broker and the software depot. Log Management and Real-time Metrics are the optional Day-N components, and they are what push worker count and size up (to `management.large`, or a 4th worker). Removing them is the biggest worker lever. A `cleanup_component.py` path exists but has a polling bug.

### Cited Findings
- Minimum set in the first instance: fleet lifecycle, Salt RaaS, SDDC lifecycle, telemetry, Salt master, identity broker and software depot. Optional after deployment: log management (LogInsight) and real-time metrics — [why-did-it.fail](https://www.why-did-it.fail/blog/2026-05-lets-talk-about-vcf-mgmt-svc/)
- Real-time Metrics needs 16 vCPU / 20 GB, which adds a worker on Small — same source. Leaha also found Real-time Metrics needs a 4th worker — [Leaha's Blog](https://blog.leaha.co.uk/2026/07/21/vcf-9-management-services-lab-downsize/)
- Log Management removal: `cleanup_component.py` (run from SDDC Manager) exits with an error when the VSP delete task reports QUEUED, because its polling only continues on RUNNING/PENDING. The component was still removed about 15 min later. Don't re-run the delete; instead poll `kubectl get components -A` until `ops-logs` is gone. After removal the workers rolled back to small — [virtualbytes.io](https://virtualbytes.io/vcf-9-1-1-worker-rightsizing-poddisruptionbudgets-and-why-it-does-not-stick/)
- With Log Mgmt in VVF, the cluster goes from 2 to 3 workers — [Lam comment](https://williamlam.com/2026/05/vcf-9-1-comprehensive-vcf-installer-sddc-manager-configuration-workarounds-for-lab-deployments.html)
- VCF Automation has no Small HA form factor and is a singleton appliance (it gets a warning in Small HA). It runs on its own "consumption" VMSP cluster of 1 or 3 nodes — [Lam, 9.1.1 enhancements](https://williamlam.com/2026/09/10-exciting-enhancements-in-vmware-cloud-foundation-9-1-1.html); [Tom Fojta / VCDX181, Downscaling VCF Automation 9.1](https://vcdx181.com/2026/05/16/downscaling-vcf-automation-9-1/) (search snippet only; full steps not read). VCFA is a 24 vCPU / 96 GB fixed size — [drpranayjha.com](https://drpranayjha.com/vcf-9-reference-architecture-design/) (search snippet)

### Inferences
- If `kubectl get components -A` on this lab shows `ops-logs` or real-time metrics, removing them is the biggest win (it lets the workers stay small and the count drop). If it shows only the Day-0 set, the workers are already right-sized, and only HA → Simple and minReplicas → 2 remain. The identity broker is listed as Day-0 here, so I found no evidence it can be removed from VCFMS.

### Gaps
- No documented procedure to undeploy Day-0 services (telemetry, depot, identity broker). This is likely impossible without breaking fleet LCM.
- The official TechDocs page for removing Log Management / Real-time Metrics through the VCF Operations UI was not retrieved.

- Ranked by risk for this lab:
  1. Remove Day-N components if any are present.
  2. HA → Simple via `cluster.ha=false`, which has been proven at 9.1.1 and saves 8 vCPU / 20 GB. Take a VCFMS backup first and expect the Postgres nudges.
  3. `cluster.worker.minReplicas=2`, which is unproven at 9.1.1 and saves 10 vCPU / 16 GB.
  4. Leaha-style pod-request trimming, which is fragile across patches.
- Redeploying fresh as 9.1.1 Simple is the only supported way to land at the smallest footprint.
